## 一、项目介绍

我最近做了一个博客平台的后端开发，从项目搭建、接口开发、数据库设计，到缓存、消息队列、容器化部署，整个流程走了一遍。

项目采用前后端分离架构，参考 RealWorld API 规范。技术栈包括：**Spring Boot 4.x**、**MyBatis-Plus**、**MySQL**、**Redis**、**RabbitMQ**。

项目已通过 Docker 容器化部署，代码托管在 GitHub 上，随时可以查看。

## 二、踩过的坑

### 2.1 启动失败：javax → jakarta 包名变更

在搭建项目时，发现应用启动不起来，控制台一直在报类找不到的错误，而且都是在找 `jakarta` 开头的类。

一开始以为是配置写错了，检查了好几遍也没发现问题。后来去查了 Spring Boot 官方文档，才知道从 **Spring Boot 3.x** 开始，包名已经从 `javax` 换成了 `jakarta`。

我项目用的是 Spring Boot 4.x，旧版的 MyBatis-Plus 依赖还是引用的 `javax` 包，所以根本启动不了。

然后我专门去 MyBatis-Plus 的官方文档里查了兼容版本，找到了 `mybatis-plus-spring-boot4-starter`，换上去之后项目就正常启动了。

## 三、数据库设计

### 3.1 整体设计

数据库一共设计了 **7 张表**：

| 表名 | 说明 |
|------|------|
| `user` | 用户表 |
| `article` | 文章表 |
| `comment` | 评论表 |
| `tag` | 标签表 |
| `article_tags` | 文章-标签关联表（多对多） |
| `favorites` | 点赞记录表 |
| `user_follows` | 关注关系表（自关联）|

用户和文章是 **一对多** 关系，文章和标签是 **多对多** 关系（通过 `article_tags` 维护）。点赞和关注也通过关联表存储，方便查询和统计。

### 3.2 面试话术

#### Q1：为什么用户和文章要分两张表？

用户和文章是两个独立的实体，存在一对多的关系。一个用户有多篇文章，把文章单独建表，既能避免数据冗余，也方便独立查询和管理。

#### Q2：为什么用 BIGINT 做 ID，不用 INT？

BIGINT 的范围更大，未来数据量增长也不用担心溢出。而且用自增 BIGINT 作为主键，查询性能也不错。

#### Q3：文章和标签为什么是多对多？

一篇文章可以有多个标签，一个标签也可以被多篇文章使用。所以我用了中间表 `article_tags` 来维护这种多对多的关系。

#### Q4：关注关系表为什么是自关联？

关注关系本质上就是用户和用户之间的关系，所以 `user_follows` 表里 `follower_id` 和 `followee_id` 都是引用 `user` 表的 `id`。这样设计扩展性好，也符合大多数社交场景的需求。

## 四、Redis 缓存

### 4.1 缓存用在什么地方

有的数据请求频率高，比如用户信息、热点文章列表。我在项目中维护了用户信息、文章信息、文章列表、标签列表的缓存数据，可以减少数据库压力。

### 4.2 缓存一致性

#### Q：如果缓存和数据库数据不一致怎么办？

数据不一致主要有两种情况：一种是并发更新，另一种是缓存更新失败。

对并发更新，我用的是 **"先更新数据库，再删缓存"** 的策略（Cache Aside Pattern）：

> 读的时候先读缓存，没有就读数据库然后写缓存；写的时候先更新数据库，然后删除缓存，让下次读重新加载。

这个方案能保证最终一致性，而且实现简单，适合大部分业务场景。

即使缓存删除失败，下一次请求会因为缓存缺失重新从数据库加载，数据最终会一致。不过缓存删除失败本身需要监控，目前还没遇到这个问题。

#### 延迟双删

- 线程 A 删缓存成功，准备更新 DB（耗时较长）
- 线程 B 读请求发现缓存为空，读取 DB 中的旧数据并写入缓存
- 线程 A 更新 DB 完成

此时缓存里是旧数据，DB 是新数据，数据不一致。第二次延迟删除就是为了解决这个问题——在 DB 更新完成后，等待一段时间（确保线程 B 的缓存写入已完成），再删一次缓存。

> 延迟时间必须 > 业务读请求的平均耗时，通常设为几百毫秒到几秒。

### 4.3 为什么不用本地缓存？

本地缓存是 JVM 内存，应用重启就没了，而且多个实例之间数据不共享。Redis 是独立服务，支持多实例共享，重启数据还在。所以像用户信息、文章数据这种全局共享的数据，用 Redis 更合适。

### 4.4 缓存雪崩

#### Q：大量 key 同时过期怎么办？

这就是缓存雪崩的问题。我的做法是给缓存过期时间加一个**随机偏移量**，比如 5 分钟 ± 30 秒，避免同一时间大量 key 同时失效，减轻数据库的瞬时压力。

### 4.5 缓存穿透

缓存穿透就是前端请求的数据在数据库里不存在，如果每次都查数据库，遇到恶意高频请求，数据库压力会很大。

#### 解决方案一：空值缓存（当前使用）

查不到数据时，缓存一个空标记，过期时间设 5 分钟。这样同一个不存在的 ID，5 分钟内不会再查数据库。

> **为什么是 5 分钟？** 太短的话恶意请求频繁还是会打到数据库；太长的话，如果期间用户真的注册了，他要等缓存过期才能正常访问。5 分钟是平衡值。

#### 解决方案二：布隆过滤器（面试补充）

空值缓存适合低频的穿透场景。如果是高频恶意攻击，比如用几万个不存在的 ID 轮流请求，空值缓存会被不断写入，内存压力会很大。

更彻底的方案是 **布隆过滤器（Bloom Filter）**——在查询前先用布隆过滤器判断 ID 是否可能存在，如果不存在就直接返回，根本不会打到数据库。布隆过滤器有一定误判率（会认为不存在的 ID 存在），但能拦截绝大多数无效请求，适合预防恶意穿透。

### 4.6 缓存击穿

缓存击穿是一个热点 key 过期瞬间，大量请求打到数据库。可以用**互斥锁**解决，只让一个线程去查数据库，其他线程等待结果。目前项目里还没遇到这个问题，如果以后遇到了，我知道怎么处理。

### 4.7 双写一致性的极端场景

#### Q：如果缓存删除失败怎么办？

目前策略：删除失败只记录日志，不阻塞主流程。

如果业务对一致性要求更高，可以用 **订阅 MySQL binlog**（如 Canal），由 binlog 变更触发缓存更新，这样缓存和数据库的同步完全解耦，不影响主业务。

## 五、AOP 日志与限流

### 5.1 日志切面

通过自定义注解加切面来实现。定义 `@Log` 注解，在需要记录日志的方法上加上该注解。

切面类用 `@Around` 环绕通知拦截加了注解的方法，记录请求参数、返回结果、耗时、操作用户、IP 等信息。

这样日志记录和业务逻辑完全解耦，代码也更干净。

### 5.2 限流

用自定义注解加 AOP 的方式实现 `@RateLimit`，可以配置每秒允许的请求数。

切面类在方法执行前用 **Guava 的 RateLimiter** 尝试获取令牌，获取不到就直接返回 429 状态码。

### 5.3 令牌桶原理

- 有一个桶，最多能放 N 个令牌
- 以固定速率往桶里放令牌
- 请求来了就从桶里取令牌，取不到就阻塞或拒绝
- 突发流量时可以累积令牌，但不会超过桶容量

### 5.4 RateLimiter 面试话术

#### Q1：acquire() 和 tryAcquire() 有什么区别？

`acquire()` 是阻塞的，如果拿不到令牌会一直等。`tryAcquire()` 是非阻塞的，拿不到就立刻返回 false。我主要用 `tryAcquire()`，因为接口请求不应该让用户一直等着。

#### Q2：RateLimiter 能支持分布式限流吗？

Guava 的 RateLimiter 是单机版的，只能限流一个 JVM 实例。如果项目部署到多台服务器，需要用 **Redis + Lua 脚本** 做分布式限流。目前我的项目还是单体部署，所以 Guava 的 RateLimiter 已经够用了。

#### Q3：RateLimiter 的预热模式是什么？

RateLimiter 有两种模式：稳定模式（`create`）和预热模式（`createWithCapacity`）。预热模式是启动时不会马上达到设定的速率，而是慢慢爬升到目标速率，适用于刚启动时瞬间流量很大、需要保护下游系统的场景。我目前用的是稳定模式。

## 七、RabbitMQ

### 7.1 使用场景

用 RabbitMQ 实现了**评论通知的异步处理**。用户评论后，主流程只保存评论，通知通过 MQ 异步发送，接口响应更快。

### 7.2 核心配置

RabbitMQ 的配置类定义了三个东西：**队列（Queue）**、**交换机（Exchange）** 和 **绑定关系（Binding）**。

- 队列：存放消息
- 交换机：决定消息往哪个队列送
- 绑定关系：把队列和交换机连起来

这样设计的好处是，不同的消息类型可以走不同的队列，互不干扰。

### 7.3 前端如何接收 MQ 消息？

前端不直接连 MQ，而是通过后端提供的接口获取通知。

| 方式 | 实现 | 适用场景 |
|------|------|----------|
| 轮询 | 前端定时调用 `/api/notifications/unread` | 简单，实时性要求不高 |
| WebSocket | 后端主动推送，建立长连接 | 即时通知（聊天、实时提醒）|
| SSE | 服务端推送事件 | 单向推送，比 WebSocket 轻量 |

## 八、MyBatis-Plus

### 8.1 MyBatis-Plus 和 MyBatis 的区别

| 特性 | MyBatis-Plus | MyBatis |
|------|--------------|---------|
| 通用 CRUD | ✅ BaseMapper 提供 | ❌ 需要手写 |
| 条件构造器 | ✅ LambdaQueryWrapper | ❌ 无 |
| 分页插件 | ✅ 内置 | ❌ 需手动实现 |
| 代码生成器 | ✅ 有 | ❌ 无 |

### 8.2 项目中的使用

主要用了三块：

1. **BaseMapper**：直接继承，基础 CRUD 不用写 SQL
2. **LambdaQueryWrapper**：动态构建查询条件，比如文章列表的分页和筛选
3. **@TableField**：处理字段映射和自动填充（`created_at`、`updated_at`）

### 8.3 分页原理

通过分页插件实现的。它会拦截 SQL 语句，自动在查询前执行 `COUNT(*)` 获取总数，然后修改原 SQL 加上 `LIMIT` 分页参数。

## 九、索引优化与慢 SQL

### 9.1 索引设计

| 字段 | 索引类型 | 原因 |
|------|----------|------|
| `slug` | 唯一索引 | 文章详情高频查询 `WHERE slug = ?` |
| `author_id` | 外键索引 | 查询某个作者的文章列表 |
| `article_id`（关联表）| 普通索引 | JOIN 查询不会慢 |

### 9.2 性能效果

`slug` 加唯一索引前，查询耗时约 80ms，执行计划是 **全表扫描（ALL）**。加索引后，耗时降到约 5ms，执行计划变成 **const 级别**。

### 9.3 Explain 验证

常用 `EXPLAIN SELECT ...` 看 SQL 的执行计划，主要看两列：
- **type**：ALL 是全表扫描，需要优化
- **key**：显示了实际用到的索引，说明走了索引

### 9.4 如何定位慢 SQL

在 MySQL 里开启**慢查询日志**，设置阈值（如 1 秒），超过时间的 SQL 会被记录下来，然后针对这些 SQL 用 EXPLAIN 分析原因。

### 9.5 关联表索引

关联表（如 `article_tags`）用的是**联合主键** `(article_id, tag_id)`，它同时起到了主键和索引的作用，而且可以防止重复数据——同一篇文章不能重复关联同一个标签。

## 十、事务

### 10.1 事务的特性

事务就是一组操作，要么全部成功，要么全部失败。在涉及关联表和多次写入的场景下特别重要。

### 10.2 传播行为

#### Q：事务的传播行为是什么？

默认是 `REQUIRED`——当前有事务就用当前的，没有就新建一个。

#### REQUIRED 和 REQUIRES_NEW 的区别

- `REQUIRED`：加入当前事务，没有就新建
- `REQUIRES_NEW`：挂起当前事务，新建一个独立的事务

通常用在日志记录这种场景——即使主业务失败，日志也要保存下来。

### 10.3 `@Transactional` 失效的场景

主要有三种：
1. **同一个类内部调用**：A 方法调用 B 方法，B 的 `@Transactional` 不生效
2. **方法不是 public**：Spring 代理只能拦截 public 方法
3. **异常被 try-catch 吞掉**：事务感知不到异常，不会回滚

我在写代码时注意了这三点，确保事务能正常生效。

## 十一、JWT 认证

### 11.1 认证流程

用户登录时，前端传邮箱和密码过来。后端用邮箱查到用户后，用 **BCrypt 的 `matches()`** 方法验证密码。验证通过后，把用户名放到 JWT 的 subject 里，设置 7 天过期时间，生成 token 返回给前端。

前端收到 token 后存在 `localStorage` 里，每次请求在 Header 里带上 `Authorization: Token xxx`。

### 11.2 拦截器验证

后端用拦截器统一处理：
1. 从 Header 取出 token
2. 验证签名和过期时间
3. 验证通过后把用户信息存到 **ThreadLocal**
4. 这样整个请求链路里都能直接拿到当前用户
5. 请求结束后在 `afterCompletion` 里清除 ThreadLocal，防止内存泄漏

### 11.3 Token 过期处理

拦截器里解析 token 时会检查过期时间，如果过期了就直接返回 401，前端收到后跳转到登录页让用户重新登录。

### 11.4 JWT vs Session

| 对比 | JWT | Session |
|------|-----|---------|
| 状态 | 无状态 | 有状态 |
| 存储 | 客户端 | 服务端 |
| 分布式 | 天然适合 | 需要共享存储 |
| 失效 | 只能等过期 | 可以主动销毁 |

### 11.5 ThreadLocal 进阶

#### Q：如果需要在异步任务里也拿到用户信息，怎么办？

普通的 `ThreadLocal` 在异步场景下会失效，因为子线程拿不到父线程的数据。

更复杂的场景会用 `InheritableThreadLocal` 传递上下文，或者用阿里巴巴的 `TransmittableThreadLocal` 解决线程池复用时的上下文传递问题。

## 十二、创建订单接口

### 12.1 接口概述

用户下单、扣库存、生成订单的完整流程，涉及并发控制、事务管理和金额精度处理。

### 12.2 核心技术点

| 技术点 | 实现方式 |
|--------|----------|
| 库存防超卖 | 乐观锁 `@Version` |
| 一致性保证 | `@Transactional` 事务 |
| 订单号生成 | 时间戳 + 随机数 |
| 金额精度 | `BigDecimal` |
| 架构模式 | 分层架构 + 统一异常处理 |

### 12.3 面试话术

#### Q：乐观锁的版本号是怎么工作的？

每次更新时，MyBatis-Plus 会自动在 WHERE 条件里加上版本号判断：
```sql
UPDATE book SET stock = stock - 1, version = version + 1 
WHERE id = 1 AND version = 0
```

如果版本号已经被其他事务改过了，更新行数为 0，说明库存扣减失败，事务回滚。

Q：如果库存扣减成功了，但订单创建失败了，数据会怎样？

不会怎样，因为扣库存和创建订单在同一个事务里，订单创建失败会触发回滚，库存会恢复。

Q：订单号为什么不用数据库自增 ID？

数据库自增 ID 会暴露业务数据量，而且不适合做订单号。我的订单号是时间戳加随机数，保证唯一的同时也有业务含义。

Q：金额用 double 会怎样？

double 和 float 存在精度丢失的问题，比如 0.1 + 0.2 不等于 0.3。金额计算必须用 BigDecimal，保证精确。

12.4 乐观锁 vs 悲观锁

对比 乐观锁 悲观锁
思路 假设不会冲突，更新时才检查 假设一定会冲突，操作前就加锁
实现方式 版本号 SELECT ... FOR UPDATE
性能 高（不加锁） 低（阻塞其他事务）
适用场景 读多写少（商品库存） 写多读少（银行账户）
冲突处理 更新失败，重试或提示用户 等待锁释放

Q：库存扣减为什么用乐观锁？

因为库存查询的频率远高于修改，用乐观锁不会阻塞查询操作。而且库存扣减冲突的概率相对较低，如果冲突了，让用户重试就行了，不需要在查询时就加锁影响系统性能。

12.5 完整回答模板

"创建订单接口实现了用户下单的核心流程。用户下单后，系统先检查库存是否充足，然后用乐观锁扣减库存，再生成订单，整个过程放在一个事务里保证一致性。库存扣减用了 @Version 乐观锁，防止高并发下的超卖问题。订单号是时间戳加随机数生成的，金额用 BigDecimal 精确计算，避免浮点数精度丢失。创建成功后，返回订单号、支付状态和 30 分钟过期时间给前端。"

十三、订单超时取消接口

13.1 业务流程

这是一个订单超时自动取消的后台任务：

1. 触发方式：用户下单后通过 RabbitMQ 发送延迟消息（30 分钟）
2. 消费处理：消息到达后消费者调用取消方法
3. 校验逻辑：检查订单存在性 → 状态必须是 PENDING → 确认已超时
4. 数据操作：先恢复库存，再更新订单状态为已取消（同一事务）
5. 并发控制：MyBatis-Plus @Version 乐观锁

13.2 为什么用 RabbitMQ 而不是定时任务？

考虑点 说明
可靠性 消息持久化，服务重启不丢失
失败重试 自带重试机制 + 死信队列
分布式解耦 订单服务和 MQ 解耦，独立中间件
削峰填谷 高峰期消息积压，消费者按能力处理
可观测性 管理界面监控积压、消费速度、失败次数

13.3 延迟消息实现

Q：延迟消息怎么实现的？

在 RabbitMQ 4.3.x 版本中，官方停止维护了 rabbitmq_delayed_message_exchange 插件，所以改用 TTL + 死信队列 方案：

1. 消息先发到 delay.queue，设置 x-message-ttl = 30 分钟
2. 消息过期后，通过 x-dead-letter-exchange 和 x-dead-letter-routing-key 自动转发
3. 消费者监听 orderTimeout.queue，处理超时取消

13.4 消息快照设计

Q：消息体带了哪些字段？为什么？

消息体包含：orderId、bookId、quantity、expireTimestamp、messageId。

核心原因是解耦和防腐——如果不带 bookId 和 quantity，消费者就要从 orders 表取数据，意味着超时取消服务依赖订单表的字段结构。未来订单表重构，超时取消服务也要跟着改。

用快照的方式，超时取消服务只依赖消息格式，不依赖订单服务的表结构。

注意：status 和 version 这种可变数据不能带，因为 30 分钟后可能已经变了。快照里的 expireTime 用于监控和解耦，数据库的 expireTime 用于最终裁决。

13.5 幂等性保证

通过订单状态保证：只有 PENDING 状态的订单才会被取消。同时用 @Version 乐观锁，updateById 返回 0 说明被其他线程修改了，抛异常让事务回滚。

13.6 异常处理策略

异常类型 处理方式
业务异常（如订单已支付） ACK 确认，不重试
系统异常（如数据库超时） NACK 重试
超过重试次数 进入死信队列 + 告警

13.7 幂等性（通用方案）

除了用业务状态做幂等，常用的方案还有：

· 唯一请求 ID：前端生成 UUID，后端用 Redis 存已处理的 ID
· 乐观锁版本号：更新时带版本条件
· 数据库唯一索引：如订单号、支付流水号

13.8 完整回答模板

"这个订单超时取消接口主要通过 RabbitMQ 延迟消息实现。用户下单后发送一条延迟消息，到期后消费者处理。处理时会检查订单状态和超时时间，然后先恢复库存再取消订单，整个过程在同一个事务中，用乐观锁保证并发安全。同时通过状态判断保证了幂等性，不会重复处理。"

## 十四、补充知识点

14.1 分布式锁

点赞防重复等场景可以用 Redis 分布式锁实现。核心是 SETNX + 过期时间 + Lua 脚本保证原子性解锁。

14.2 雪花算法（Snowflake）

生产环境生成全局唯一 ID（如订单号）的推荐方案。64 位长整型，由时间戳 + 机器 ID + 序列号组成。

14.3 ConcurrentHashMap

方案 线程安全 性能 说明
HashMap ❌ 最高 并发扩容可能死循环（JDK 1.7）或数据丢失
Hashtable ✅ 低 全表锁，性能差
ConcurrentHashMap ✅ 高 细粒度锁（Node 锁），只锁当前操作的 key

14.4 synchronized 底层原理

基于 JVM 的 monitor（监视器锁）机制，锁升级过程：

1. 偏向锁：单线程访问，记录线程 ID
2. 轻量级锁（自旋锁）：多线程交替访问，CAS 自旋等待
3. 重量级锁：竞争激烈，线程挂起阻塞

JVM 根据竞争程度自动升级锁，锁信息存储在对象头（Mark Word）中。
